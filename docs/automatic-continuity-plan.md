# 自动上下文接续重构方案

日期：2026-09-20。

状态：**目录切换与生命周期对账修复、主会话复核及本地安装验证已完成，补丁版本为 v0.3.1。** 本地安装验收使用保留 0.3.0 元数据的同一修复实现；v0.3.1 只在该候选上增加版本元数据变更，完整离线套件再次通过。已有用户进程没有被自动重启或热替换。发行状态以 [v0.3.1 Release](https://github.com/macchen123/claude-context-continuity/releases/tag/v0.3.1) 为准。本页是本次工作的唯一方案，详细验证历史见 [原生接续验证记录](native-continuity-fix-validation.md)。

## 目标与范围

cclaude 只负责在下一次模型请求前管理上下文容量：预算充足则继续，接近边界则完成交接、换到新窗口继续。旧信息由模型按需通过 History/Notes 查回，不引入任务类型、任务完成判定器或第二套业务状态。

自动监测贯穿正常运行和可恢复故障。历史暂未写完、通道暂不可用或确认迟到时，持续观察并在条件满足后继续；不能把临时等待变成永久停用。原生恢复后，重新绑定实际会话与用量。为保护容量而暂缓模型生成，与停用自动管理是不同的事情。

源码重构阶段只修改并验证候选，保持 v0.2.7 安装和发布资产不变。用户在源码验收后明确授权安装并更新远程，版本按功能更新提升为 v0.3.0；已有会话记录和历史发布资产仍保留，现有用户会话由用户自行重启。此前本地的等待期间预算保护修复保留，并纳入本次验收。

## 不可放宽的边界

- 继续使用原生 Claude Code、既有控制通道、History/Notes 和唯一 context 状态；不增加运行组件、独立输入队列或权限系统。
- 未开始写出命令字节的失败可等待重试；一旦开始写出，结果未知时只核对原生事实，不盲目重发清屏、交接或工具操作。
- 不因换窗重跑业务任务，不丢失已提交输入、已完成结果或必要历史来源。后台任务不必结束才能换窗。
- 原生权限和用户取消始终有效；交接、通知和恢复回执不提供新的用户授权。
- 测试只操作新建隔离实例，使用 localhost 脚本模型；不调用外部付费模型，不读写已有用户终端，不保存凭证。

## 已核对的原因

1. 旧实现的 `paused` 阻断控制器推进，但模型仍可能继续消耗窗口。此前预算保护解决了后半部分，本次进一步取消了粘滞的停用状态。
2. 45 秒确认超时、历史暂不可读等被当作放弃恢复的条件；控制器遇到一般异常还会退出。现在超时只说明等待条件，观察继续。
3. 首条人类记录尚未落盘与会话身份错误曾共用失败路径；旧执行中的 pending 标记又阻止真实 `/resume` 重新绑定。预算观察、授权核验和当前执行生命周期现在分别处理。
4. 实测 Claude Code 2.1.278 会消费并移除自身的背景通道环境变量。原方案中“hook 会继承这些原生变量”的假设不成立；改为在 cclaude 自有的进程环境变量中保留同一份原有控制能力，按准确 context/socket 校验后恢复观察者。凭证不进入 argv、插件文件、状态或回执。
5. 原生冷恢复中，写入后立即关闭通道可能导致清屏没有被消费。现有协议支持 `repaint` 的顺序响应：保持同一次连接直到该响应到达，再关闭连接，不加固定睡眠、不重发命令。这个响应不等于清屏或交接成功，成功仍由真实 `SessionStart` 和历史记录确认。

## 最终实现

保留一条链路：`原生 hook / 当前会话事实 → 预算与持久交接请求 → 等待直接工具结算 → 原生清屏 → 新会话确认 → 原生交接入史 → 下一轮`。

1. **等待与窗口阶段分开。** 等待记录保留最后一个准确阶段，观察者持续协调迟到确认、完整历史前缀及临时读写失败。旧 `paused` 状态依据已有控制记录迁移，不重放未知操作。
2. **真实恢复先绑定，再启动监测。** 原生 `SessionStart` 核验 SID、路径和工作目录后建立当前执行生命周期；A→B→A 和有新工作后的重复同 SID 恢复都能重新绑定。旧工具、清屏和交接标记仅保留为历史事实，不能阻止新生命周期，也不能授权旧命令重跑。
3. **观察不依赖首条指令已经可分类。** 预算可使用准确绑定的完整原生前缀；自动清屏和交接仍核验真实人类指令、hash 和历史关联。直接工具的开始／结算事实先于易失败的历史读取记录，避免瞬时读取错误丢失活动工具。
4. **监测进程自动恢复。** 受管启动提前标记观察者职责；真实 hook 在处理会话事件后，使用内存中的同一控制能力和既有单控制器锁恢复观察者。正常启动、hook 恢复和手动高级入口复用一个启动函数；外部 attach 不获得凭证或伪造事件。
5. **准确结算输入与交接。** 已确认清屏后的空窗或只有未执行输入的窗口可继续原交接；新窗口已经开始工作时，不注入旧 handoff。交接确认只结算该次快照实际包含的输入记录，后来到达的人类输入和原生通知按原顺序保留，经下一次真实批次／Stop 边界进入既有接续路径。
6. **保持预算保护与未知投递边界。** 等待期间仍可暂缓超预算请求，保留原生结果和提交记录。传输只发送一次；拒绝、断连、畸形／超大回执和超时均不能冒充“没有发送”或换窗成功。

## 文件映射

- `context_runtime.py`：非终止式等待、预算／授权观察解耦、工具生命周期及旧事件区分。
- `tui_runtime.py`：连续阶段协调、原生恢复、输入结算、活动新窗保护和单观察者恢复。
- `native_control.py`：未发送与结果未知的区别、仅内存的 hook 通道能力、原生顺序响应。
- `continuity.py` / `native_entry.py`：唯一 hook／启动入口；不把无法识别的交互调用静默降为无监测运行。
- 对应单元测试、`native_runtime_probe.py`、`native_continuity_probe.py`：离线反证与真实原生宿主连接。
- 中英文 README 与既有验证文档：同步实际行为和安装／发布边界。

## 首次失败与修正边界

- v0.2.7 正常三轮基线通过，2.737 秒；真实进程恢复被旧 pending 操作阻挡，90.505 秒内仅完成 1/3 次转换；真实 `/resume` 未恢复已退出观察者，90.372 秒内完成 0/3 次转换。
- 第一份候选正常三轮通过，3.177 秒；冷恢复未消费清屏和 hook 缺少原生通道环境导致的失败均保留。环境存在性只记录布尔值，未记录凭证。两处原生连接修正后完成上述最终验收。
- 主会话和独立审查发现的旧事件误过滤、旧 handoff 误投、观察者启动顺序、迟到确认误结算及重复恢复问题均有首次反证和回归。执行者自审补上了临时历史读取失败时的直接工具保护。
- 探针早期的未提交输入、可变长 CLI 参数、缺失中间用户回合，以及把清屏空窗的 UI 元数据当作任务历史等夹具问题单独记录，不计作产品通过或隐去首次失败。
- 核心执行者和闭合复核各遇到一次连接中断，均核对已有产物后续接同一上下文，没有重放副作用。

## 交付边界

本次证明了上述原生宿主连接、恢复与无重放路径，不等同于外部模型自主长任务测试，也没有实际使 VS Code 闪退。其他原生版本仍需适用的兼容性检查；已运行的旧会话不会因源码修改而热升级。

源码、方案与验证记录已同步；源码验收后获授权的 v0.3.0 离线构建、安装和安装目录验证也已通过。安装后的冷恢复和观察者恢复各完成三次换窗，后台／输入／存档检查通过；具体结果及 wheel SHA256 见验证记录。更新安装不会热升级已有会话，用户自行正常退出并重新启动或恢复。

## 2026-09-21：目录切换与生命周期对账修复

实际长任务发现一个反例：原生 Bash 合法切换到项目子目录，工具结果已经落盘，但完成 hook 因固定 cwd 检查而没有结算 pending。随后旧回合被预算保护暂停，控制器又被过期 pending 阻止换窗。手动清屏还会把该前台标记带入新窗口。因此“观察者一直运行”并不等于“换窗流程一定能够推进”。

本次修复继续复用原生通道、唯一 context 状态和 History，不增加管理器或输入队列：

1. 主会话 hook 先核对准确 SID 和原生历史路径，再接受宿主报告的当前工作目录，并从该目录读取有效配置。目录不是会话身份；其他 context 的恢复授权核验仍保留。
2. 在真实工具批次或 Stop 边界，根据同一调用的原生请求与终态回执结算漏掉的 hook。没有调用记录、只有输出正文、其他 sidechain 的结果或没有终态回执，都不能证明完成。
3. 原生 `SessionStart(clear)` 确认新的前台执行周期。旧前台标记只保留为迟到回执的历史记录，不能阻止新窗口；真实后台任务继续保留。
4. 对已有残留，只从当前 context 已登记的准确历史来源查找完成证据；未知仍保留，不按静默时长删标记。原生失败通知可结算子代理，后续恢复的同 ID 任务不能被先前失败误关闭。
5. 保持用户取消、身份核验和投递未知时不盲目重发的边界。后台历史暂不可读不能成为等待所有后台任务的新增条件。

验收使用新增离线回归和现有原生探针的目录切换场景。必须证明：合法 cd 后不补发用户消息即可连续换窗；受影响操作只执行一次；真实未完成工具不会被提前结算；跨会话记录不会被误用。原生探针仍使用隔离实例和 localhost 脚本模型，不以此声称所有外部模型长任务都不会失败。

首次新增 8 项回归中 6 项失败、2 项保护检查通过，已保留失败。第一轮扩大检查为 156 项通过、2 项恢复目录相关失败；完整离线初跑为 291 项通过、2 项失败，其中一项是 macOS `/var` 临时目录别名未规范化的夹具问题。

2026-09-21 接续验证：首轮完整离线套件 293 项及 171 个 subtest 通过。独立复核与主会话反证发现并集中修正了三处边界：延迟历史不能跳过跨目录恢复核验，合法 cd 后可依据准确 owner 的启动目录冷恢复，旧窗口同 ID 的结果不能结算新窗口刚开始的调用。未验证的恢复来源也不提前进入已验证历史目录，避免后续恢复把临时登记误当成证明；新增真实 PreToolUse 的来源绑定只记录在既有 context state 中。

最终完整离线套件 **297 项及 175 个 subtest 通过，8.94 秒**；真实 cd 后从原启动目录冷恢复并连续三次换窗 **通过，6.857 秒**；清屏后的冷恢复三轮 **通过，3.798 秒**；观察者恢复三轮 **通过，4.203 秒**；后台／输入／历史／存档 **通过，12.122 秒**。实际受影响历史和当前登记来源经过修复后的 consumer 只读核对，内存中的旧 pending 被准确结算，真实未完成调用保留，持久 state 未变。主会话已完成范围复核与验收。随后用户明确选择本地安装并验证：使用既有构建工具离线生成并安装修复候选，14 个安装模块与源码／wheel 逐字节一致，依赖和 CLI 入口目标不变。从实际安装目录再次完成 cd＋冷恢复三轮（6.813 秒）、观察者恢复三轮（4.304 秒）和后台／输入／存档（11.904 秒）。修复候选保留 0.3.0 元数据，未创建新发布；已有用户进程及远程资产未改动，完整加载修复仍需正常退出旧进程后重新启动。
